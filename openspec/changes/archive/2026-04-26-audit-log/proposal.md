# Audit log for sensitive entities

## Why

The system stores data that matters when something goes wrong:

- **Pets** — vaccination records, medical notes, deworming dates, behavioural attributes that affect compatibility decisions.
- **Owners** — contact info, emergency contact, vet relationships.
- **MedicalNotes** — allergies, post-op follow-ups.
- **Vaccinations** — dates and types relied on by the notification cron.

Today, an edit to any of these is a destructive overwrite: there's no record of who changed `Bruno`'s temperament from `aggressive` to `friendly`, or when `Mía`'s rabies date was updated from 2024-06-01 to 2025-06-01. When an owner says "you have the wrong vaccination date," staff have no way to reconstruct what happened.

This is also a non-trivial compliance lever in any jurisdiction with veterinary record-keeping rules — "we changed it" is not a defensible answer when the change wasn't logged.

## What

Adopt `django-simple-history` (the de-facto auditing library for Django, ~3.4K GitHub stars, maintained, no external infrastructure). It works by:

1. Adding a `HistoricalRecords()` field to each tracked model.
2. Auto-generating a sister table (`historical<modelname>`) per model.
3. Recording one row per insert / update / delete with the change type (`+` / `~` / `-`), a timestamp, and the user who made the change (resolved from the request middleware).

We add it to four models:

- `Pet`
- `Owner`
- `MedicalNote`
- `Vaccination`

We do NOT track `Schedule`, `Notification`, `NotificationTemplate`, `NurserySetting`, `User`, `Vet`, or `VaccinationType` for this v1:

- `Schedule` rows are short-lived (deleted / completed quickly); auditing them would generate massive history with low value.
- `Notification` rows are derived from the cron; the source of truth is upstream.
- `User` audit is a security concern of a different shape (role escalations, password changes) better handled through Django's `auth_log` or a dedicated approach.
- The remaining models change rarely enough that the history isn't worth the column.

## Impact

- New dependency: `django-simple-history` in `backend/requirements.txt`.
- New `INSTALLED_APPS` entry: `'simple_history'`.
- New middleware entry: `'simple_history.middleware.HistoryRequestMiddleware'`.
- One field per tracked model: `history = HistoricalRecords()`.
- One migration per tracked model auto-generated by `manage.py makemigrations`.
- Read-only admin endpoints to query history for a given record (admin-only):
  - `GET /api/pets/<id>/history/`
  - `GET /api/owners/<id>/history/`
  - `GET /api/pets/<pet_id>/medical-notes/<id>/history/`
  - `GET /api/pets/<pet_id>/vaccinations/<id>/history/`
- A small `HistorySerializer` returning `{ history_id, history_date, history_user, history_type ('+' | '~' | '-'), changed_fields, … }`.

## Out of scope

- Frontend UI for browsing history. v1 is API-only — staff can use the Django admin or a curl one-liner. A future change can add an "Activity" sidebar to each detail view; until there's a concrete need we don't speculate about what it should look like.
- Soft-delete. The library naturally records deletes; we don't change the delete-cascade behaviour.
- Cross-entity reports ("everything that changed in the last 24 hours"). The history tables are queryable; we'll add reports if a real use-case materialises.
- A retention policy for old history rows. Disk is cheap; if/when this grows past 100k rows the cleanup is a five-line Django management command.
