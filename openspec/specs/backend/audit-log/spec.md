# Backend / Audit Log

## Purpose

The system stores data that matters when something later goes wrong: pet temperament and dominance attributes that drive compatibility decisions, owner contact details, medical notes, and vaccination dates. An edit to any of these used to be a destructive overwrite — staff had no way to reconstruct who changed what, when, and to what value.

The audit-log capability records every insert / update / delete on these four entity types, attributes the change to the calling user when the change goes through a request, and exposes per-entity history reads to admins.

## Requirements

### Requirement: Pet, Owner, MedicalNote, and Vaccination edits SHALL be recorded in a per-entity history table

The system SHALL record every insert, update, and delete on `pets.Pet`, `pets.Owner`, `pets.MedicalNote`, and `pets.Vaccination` in a sister history table generated by `django-simple-history`. Each history row SHALL carry:

- The full snapshot of the entity's fields at the time of the change.
- `history_id` (PK).
- `history_date` (timestamp).
- `history_user_id` (FK to `User`; `NULL` when the change happened outside a request, e.g. a management command).
- `history_type` — one of `+` (create), `~` (update), `-` (delete).
- `history_change_reason` (text, nullable; reserved for explicit operator notes).

History tables SHALL be migration-generated; they MUST mirror the live entity's schema verbatim plus the `history_*` columns.

#### Scenario: A staff member edits a pet's temperament

- GIVEN user Alice is logged in
- AND a `Pet` row exists with `temperament = "playful"`
- WHEN Alice `PATCH /api/pets/<id>/` with `{"temperament": "calm"}`
- THEN one new row SHALL be inserted in `historicalpet` with `history_type = "~"`, `history_user_id = Alice.id`, and the post-change snapshot

#### Scenario: A management command write is anonymous

- GIVEN no HTTP request context
- WHEN `seed_example_data` updates a tracked entity
- THEN the resulting history row SHALL have `history_user_id = NULL`

#### Scenario: Bulk operations leave no history (documented caveat)

- GIVEN a developer issues `Pet.objects.filter(...).update(temperament="calm")`
- THEN no history row SHALL be created for any of the affected pets
- AND this caveat SHALL be documented in `backend/AGENTS.md` so future work avoids `bulk_update` / `update()` on tracked models

### Requirement: Per-entity history SHALL be readable by admins

The system SHALL expose per-entity history under a `history` sub-resource of each tracked entity:

- `GET /api/pets/<id>/history/`
- `GET /api/owners/<id>/history/`
- `GET /api/pets/<pet_id>/medical-notes/<id>/history/`
- `GET /api/pets/<pet_id>/vaccinations/<id>/history/`

These endpoints SHALL be admin-only (`role = "admin"`). Non-admins SHALL receive HTTP 403; unauthenticated callers SHALL receive HTTP 401.

The response body SHALL be an array of history rows ordered by `history_date` descending, each row including `history_user.{id, email}` (denormalised for convenience), `history_type`, `history_date`, and the entity snapshot.

#### Scenario: Admin reads pet history

- GIVEN user Alice has admin role
- AND pet 17 has 3 historical rows
- WHEN Alice `GET /api/pets/17/history/`
- THEN the response SHALL be HTTP 200
- AND the body SHALL be an array of 3 rows, ordered most-recent first

#### Scenario: Non-admin is refused

- GIVEN user Bob is a non-admin authenticated user
- WHEN Bob `GET /api/pets/17/history/`
- THEN the response SHALL be HTTP 403

#### Scenario: Unauthenticated read is refused

- GIVEN no Authorization header
- WHEN the caller `GET /api/pets/17/history/`
- THEN the response SHALL be HTTP 401

#### Scenario: Medical note nested URL validates pet membership

- GIVEN medical note 5 belongs to pet 1
- AND user Alice is admin
- WHEN Alice `GET /api/pets/2/medical-notes/5/history/`
- THEN the response SHALL be HTTP 404

### Requirement: A unified activity feed SHALL expose a chronologically merged stream of changes across all tracked entities

The audit log SHALL expose `GET /api/audit-log/activity/` as an admin-only endpoint that returns a paginated, filterable stream of history rows across all tracked entities (currently Pet, Owner, MedicalNote, Vaccination).

The response body SHALL have shape:

```json
{
  "count": <int>,
  "results": [
    {
      "entity_type": "pet" | "owner" | "medical_note" | "vaccination",
      "entity_id": <int>,
      "entity_label": <string>,
      "history_id": <int>,
      "history_type": "+" | "~" | "-",
      "history_date": <ISO 8601>,
      "history_user": { "id": <int>, "email": <string> } | null
    },
    ...
  ]
}
```

`entity_label` SHALL be a human-readable label derived from the historical row's snapshot (Pet → `name`; Owner → `first_name + ' ' + last_name`; MedicalNote → `title`; Vaccination → `vax_type`).

Results SHALL be sorted by `history_date` descending. `count` SHALL be the total number of rows matching the filter set (across all entities), independent of pagination.

The endpoint SHALL accept the following filter query params:

- `entity_type`: one of `pet|owner|medical_note|vaccination`. Unknown values → 400.
- `action`: one of `+|~|-` (matches `history_type`). Unknown values → 400.
- `user`: integer; matches `history_user_id`. Non-integer → 400; unknown id → 0 results, not 400.
- `since` / `until`: ISO 8601 timestamps; bound `history_date`. Bad format → 400.
- `limit`: integer, default 50, silently clamped to `[1, 200]`.
- `offset`: integer, default 0; negative → 400.

Permission SHALL match the existing per-entity history endpoints: admin-only (`role='admin'`), 401 for unauthenticated callers, 403 for non-admins.

#### Scenario: Admin reads the unified feed

- GIVEN user Alice has admin role
- AND the system has 4 history rows (one per tracked entity)
- WHEN Alice `GET /api/audit-log/activity/`
- THEN the response SHALL be HTTP 200
- AND the body SHALL include `count: 4` and 4 result rows
- AND the rows SHALL include all four entity types
- AND the rows SHALL be sorted by `history_date` descending

#### Scenario: Filter by entity_type narrows the feed

- WHEN Alice `GET /api/audit-log/activity/?entity_type=pet`
- THEN the response SHALL be HTTP 200
- AND every result SHALL have `entity_type == 'pet'`

#### Scenario: Filter by action returns only matching history_type

- GIVEN there are creates ('+') and updates ('~') in the log
- WHEN Alice `GET /api/audit-log/activity/?action=~`
- THEN every result SHALL have `history_type == '~'`

#### Scenario: Unknown filter values reject with 400

- WHEN Alice `GET /api/audit-log/activity/?entity_type=mystery`
- THEN the response SHALL be HTTP 400
- WHEN Alice `GET /api/audit-log/activity/?action=wat`
- THEN the response SHALL be HTTP 400
- WHEN Alice `GET /api/audit-log/activity/?since=not-a-date`
- THEN the response SHALL be HTTP 400

#### Scenario: Non-admin is refused

- GIVEN user Bob is a non-admin authenticated user
- WHEN Bob `GET /api/audit-log/activity/`
- THEN the response SHALL be HTTP 403

#### Scenario: Pagination with offset beyond total returns empty results

- GIVEN there are 4 history rows total
- WHEN Alice `GET /api/audit-log/activity/?offset=999`
- THEN the response SHALL be HTTP 200
- AND `results` SHALL be an empty array
- AND `count` SHALL still be 4

### Requirement: The activity feed endpoint SHALL be gated by the `activity_logs` feature flag

The unified activity feed endpoint (`GET /api/audit-log/activity/`) SHALL be gated by the `activity_logs` feature flag. When the flag is `enabled = False`, the endpoint SHALL return HTTP 404 to authenticated admins, mirroring the "page does not exist" framing used for other gated surfaces. The feature gate SHALL run AFTER the auth + admin permission checks so an unauthenticated caller continues to receive 401 and a non-admin continues to receive 403 — the surface's existence is not leaked to unauthorised readers via the gating shape.

The per-entity history endpoints (`GET /api/pets/<id>/history/` etc.) SHALL NOT be gated by this flag; they remain reachable so admins can still drill into a single entity's history when the cross-entity feed is hidden.

#### Scenario: Admin gets 404 when the flag is off

- GIVEN user Alice has admin role
- AND the `activity_logs` feature flag is `enabled = False`
- WHEN Alice `GET /api/audit-log/activity/`
- THEN the response SHALL be HTTP 404

#### Scenario: Non-admin gets 403 even when the flag is off

- GIVEN user Bob is a non-admin authenticated user
- AND the `activity_logs` feature flag is `enabled = False`
- WHEN Bob `GET /api/audit-log/activity/`
- THEN the response SHALL be HTTP 403 (the admin gate runs before the feature gate)
